# OPTIMIZATION.md — журнал производительности

Как игра ускоряется: что уже сделано, как это замерять, что сторожат тесты —
и ГЛАВНЫЙ ЗАКОН, который стоит выше любого бенчмарка.

---

## ⚡ ЗАКОН №0 — ЧИТАТЬ ПЕРВЫМ

> **ОПТИМИЗАЦИЯ НИКОГДА НЕ СТОИТ ВЫШЕ ЭСТЕТИЧЕСКОЙ / АУТЕНТИЧНОЙ /
> ВАЙБОВОЙ / ВИЗУАЛЬНОЙ ПРИВЛЕКАТЕЛЬНОСТИ ИГРЫ.**
>
> **НИКОГДА, НИ ПРИ КАКИХ УСЛОВИЯХ НЕ УБИРАТЬ ЧТО-ТО ИЗ ВИЗУАЛА, ЧТОБЫ
> ИГРЕ БЫЛО «ЛЕГЧЕ». ЭТО НЕ ОПТИМИЗАЦИЯ — ЭТО ПРОВАЛ.**

Оптимизация — это сделать ТУ ЖЕ красоту дешевле, а не нарисовать МЕНЬШЕ
красоты. Свечения, золотые рамки, лаковый занавес, дождь победы, золотой
ринг матча, пыль в меню, каллиграфия, звуки и музыка — это не «накладные
расходы», это и есть продукт.

### Как отличить оптимизацию от провала

| Оптимизация ✅ | Провал ❌ |
| --- | --- |
| Тот же golden ring рисуется без перекраски всей доски | Убрать golden ring — «он дорогой» |
| Пружина позы фишки осталась, но перестала дёргать layout | Укоротить или выключить пружину |
| Занавес между экранами красится один раз, на композитном слое | Убрать занавес |
| Тень фишки отдаётся браузеру через transform-слой | Снять тени со всех фишек |
| Музыка играет дальше, а статтер ушёл | «Выключим музыку — станет плавнее» |

### Контрольный вопрос перед merge

> «Изменился ли ХОТЬ ОДИН пиксель в полном режиме (Full) на обычном ПК?»
>
> Правильный ответ: **НЕТ**. Изменился в сторону беднее — откатить правку
> и искать другой способ. Тест на красивость всегда раньше теста на скорость.

Порядок приоритетов при любом споре:
**Красота → Вайб → Плавность → Скорость → Размер кода.**

### Единственное исключение — и то с оговоркой

«Лёгкий режим» (v32, `js/perf.js` + `css/lite.css`) — единственный законный
механизм, который упрощает картинку, потому что:

1. он включается ТОЛЬКО на действительно слабом железе (режим auto) или
   рукой самого игрока;
2. он не трогает игровые подсказки (золотые свободные фишки, приглушённые
   закрытые) и общую композицию: стол, рамку, медальон, каллиграфию;
3. полный режим (Full) остаётся нетронутым для всех остальных.

Лёгкий режим — это **костыль для слабых машин, а не лицензия** упрощать
основную игру. Любая новая «оптимизация», отключающая визуал в Full,
нарушает Закон №0.

## Журнал: v46-perf — «Большие доски без статтеров»

Жалоба игрока: «много статтеров, при огромном количестве фишек играть почти
нереально» (актуально после v45, поднявшего кап Микса до 600 фишек).

### Диагноз — что именно тормозило

1. **Базовый `transition` у `.tile` анимировал `box-shadow` (13 слоёв) и
   `filter`.** После каждого матча класс `.free` переворачивается у десятков
   фишек, и каждая из них 0.3 с перерисовывает свою многослойную тень и
   saturation/brightness — главный статтер хода на больших досках.
2. **`setSelected` на каждый клик обходил ВСЕ фишки** — до 1200 бессмысленных
   `classList`-проверок при 600 фишках.
3. **Счётчик ходов в шапке** — свой O(free²) цикл в `play.js`, хотя быстрый
   O(free) `Game.countAvailableMoves` уже существовал.
4. **`positionTile` безусловно писал `width/height`** — до 1200 пустых
   записей стиля на каждый reposition.
5. **`lite.css` не гасил `drop-shadow` на SVG-лицах** — до 600 фильтров на
   каждую перекраску в лёгком режиме.
6. **`fitBoard` при скрытом экране** оставлял размер СТАРОЙ доски → первый
   кадр малой партии после гиганта мигал «как бы издалека»
   (v45 чинил только превью Микса, это чинит старт партии).

### Исправления

Каждое — «рисуем то же самое дешевле»; ни один пиксель Full-режима не изменился.

1. Базовый transition = `transform` + `opacity` (+ translate/scale/rotate);
   поза по-прежнему пружинит. У `.matching` свой локальный transition с
   filter — но это 2 фишки за матч, не вся доска.
2. `setSelected` через трекинг `selectedEl`/`candEls` (сброс трекинга в
   `renderFull`, иначе классы утекут между партиями).
3. Шапка считает ходы через `Game.countAvailableMoves()`.
4. `positionTile` пишет размер только при реальном изменении.
5. lite: `.tile .tile-face-svg { filter: none }`.
6. Фолбэк `fitBoard` → `estimateStage(window, { uiScale, loupe })` — оценка
   сцены по окну, пока игровой экран скрыт.

### Замеры (раскладка «Крест», 202 фишки, JS-часть)

| Операция | Время |
| --- | --- |
| newGame | 18.6 мс |
| renderFull | 17.1 мс |
| reposition | 42 мс |
| после матча: getFreeTiles | 0.3 мс |
| после матча: hasAnyMove | 0.2 мс |
| после матча: countAvailableMoves | 0.2 мс |
| после матча: highlightFree | 0.7 мс |

JS больше не узкое место: основной выигрыш дала покраска/композит — переход
на transform/opacity, то есть ровно «та же красота, дешевле нарисованная».

### Сторожа и выпуск

- `tests/perf46.test.js` (8 тестов): transition без box-shadow/filter; нет
  `will-change` на всех фишках; `setSelected` без обхода всех фишек + сброс
  в `renderFull`; шапка через `Game`; `fitBoard` → `estimateStage`; lite
  без drop-shadow на лице; `positionTile` пишет размер только при изменении.
- Прогон: `node tests/run.js` → **1539 passed, 0 failed**; smoke-dom →
  ERRORS: 0.
- `sw.js`: `CACHE_NAME` → `mahjong-v46-perf`.

## Журнал: v47-perf — «Алгоритм дешевле, картинка та же» + шрифты по кнопке

Запрос игрока: серьёзная оптимизация «на вырост» и критический разбор
народных советов (rAF, пулы объектов, canvas-трюки, CSS-композит).
Бенчмарк логики в Node (песочница tests/load.js) до правок показал,
где жарко на самом деле:

| Операция (vm, до → после) | до | после | выигрыш |
| --- | --- | --- | --- |
| newGame, Микс-600 | 1719 мс | 66 мс | ×26 |
| getFreeTiles, 600 фишек | 13,3 мс | ~0 (кеш) | пересчёт 1/ход |
| countAvailableMoves, 600 | 13,1 мс | 0,02 мс | ×650 |
| логика 40 матчей, Микс-600 | 2205 мс | 445 мс | ×5 |
| сериализация сейва, 600 | 0,28 мс | 0,27 мс | без изменений — и не надо |

### Диагноз

1. `getFreeTiles` — O(N²): `isFree` сканирует ВСЮ доску дважды, а за один
   ход игрока его зовут 3–4 раза (highlightFree, hasAnyMove,
   countAvailableMoves, setSelected при «Показывать пару»). На Миксе-600 —
   ~40–50 мс чистой логики на каждый матч.
2. `hasAnyMove` — O(free²) попарных `isMatch` после КАЖДОГО матча, хотя
   инвариант `matchKeyOf ⟷ isMatch` уже использовался в
   `countAvailableMoves` (v46).
3. `buildRemovalOrder` (раздача новой партии и перемешивание) — O(N³):
   на каждом шаге «разборки» `spotIsFree` заново сканировала весь остаток
   для каждой позиции. На Миксе-600 newGame стоил ~1,7 с.
4. `movesInPlacements` — O(N²) на каждый из 5 try.

### Исправления

1. **Кеш свободных фишек + z-бакеты** (`js/game.js`): свободность меняется
   только при мутации доски — пересчёт один на ход; сам пересчёт ходит по
   слоям (накрывшие — в z+1, соседи — в z), что спускает его с O(N²) до
   O(N·слой). Кеш сбрасывается в ВСЕХ мутаторах (матч, отмена,
   redealSolvable, applyArrangement, rebuildBoardKeys, swapTileToSpot,
   rescueByCopyingIdentity, newGame) + страховка-сигнатура (state/tiles/
   removedCount) ловит и прямую подмену доски сейвом (saves.js явно зовёт
   `Game.invalidateFreeCache()`).
2. **hasAnyMove через группировку** — O(free²) → O(free), ровно тот же
   инвариант, что у countAvailableMoves.
3. **buildRemovalOrder O(N³) → O(N² + N·k·слой)**: свобода позиций
   хранится инкрементально, после снятия пары пересчитывается только у её
   соседей. Порядок списка свободных и ПОСЛЕДОВАТЕЛЬНОСТЬ вызовов rng —
   бит-в-бит прежние.
4. **movesInPlacements по z-бакетам** — результат совпадает бит-в-бит.
5. **Клик-путь** (`js/app/play.js` + `js/render.js`): элемент фишки из
   карты `Render.getTileEl(tile)` / `Render.getSelectedEl()` вместо
   `document.querySelector` по всему документу на каждый клик мимо.
6. **Автосейв не тронут**: сериализация 600 фишек — 0,28 мс; совет
   «дебаунсить сохранение» отклонён по данным, без единой правки.

### Гарантия идентичности досок (Закон №0 для логики)

Порядок вызовов rng в раздаче сохранён: 22 golden-сцены (6 раскладок ×
3 seed + Микс-600 + серии матчей/отмена) сняты ДО рефакторинга и зашиты
в `tests/perf47.test.js` — доски для тех же seed совпадают хэш-в-хэш.
Предикат свободности и hasAnyMove сверены с наивными копиями исходного
кода на всех стадиях партии (6 раскладок доиграны до конца). Ни один
пиксель Full-режима не изменился — менялся только алгоритм.

### Народные советы: применено / отклонено

- **rAF вместо setInterval** — отклонено: пер-кадрового цикла в игре нет
  (рисование событийное, DOM/CSS). Оба setInterval легитимны: музыка —
  планировщик с горизонтом 1,2 с (rAF в фоновой вкладке останавливается и
  музыку уронил бы), часы — тик раз в секунду. rAF уже стоит там, где
  нужен: сторож кадров (perf.js), FLIP-зум, лупа.
- **Пул объектов (new Bullet)** — как буквальный пул НЕ применён: в игре
  нет пер-кадровых аллокаций; искры/кольца создают 12–20 элементов РАЗ за
  матч и удаляются. Идея же переиспользования реализована там, где она
  окупается: кеш free-массива вместо пересоздания на каждый вызов.
- **Группировка по цветам / батчинг путей / OffscreenCanvas / округление
  координат** — неприменимы: рисует не canvas, а DOM/CSS. Canvas —
  однократная растеризация знака в mixglyph (уже с willReadFrequently).
  Округление координат фишек ВРЕДНО: слои перекрываются, целочисленные
  left/top дают 1px-щели — визуальный дефект, прямое нарушение Закона №0.
- **transform вместо left/top** — миграция позиции фишки сознательно
  отложена (см. «Исследовано, но НЕ слито» ниже); left/top пишутся
  разово при построении/ресайзе, не на каждый кадр. Анимации давно на
  transform/opacity (v46).
- **will-change** — запрещён анти-паттерном (600 фишек = 600 GPU-слоёв),
  сторожится тестом v46.
- **position: absolute у игровых объектов** — уже так: `.tile` абсолютен
  с самого начала (tiles.css).

### Шрифты по кнопке (находка: fonts/ и css/fonts.css отсутствовали)

В рабочей копии не было `fonts/` и `css/fonts.css`, хотя их кэшировал
sw.js, подключал index.html и требовал тест v20 — игра жила на системном
фолбэке и тема «проседала». Решение v47: **бинарников шрифтов в
репозитории нет** (`.gitignore: fonts/`, sw.js кэш чист), а модуль
`js/fonts.js` подключает их тремя путями по приоритету:

1. IndexedDB — уже загруженные шрифты восстанавливаются мгновенно;
2. папка `fonts/` рядом с index.html (мини-архив «Шрифты», 9 файлов,
   ~460 КБ — субсеты ровно тех ~350 символов, что игра рисует);
3. кнопка в меню/настройках — докачка с Google Fonts: разбираем css2,
   берём только блоки unicode-range, пересекающиеся с набором символов
   игры, кладём в IndexedDB. Один раз — дальше офлайн.

Пока шрифтов нет — системный фолбэк (как и было). Ничего не качается без
клика игрока. Проверено e2e в Chromium: локальный путь, восстановление из
IndexedDB, CDN-путь (через мок css2; сами эндпоинты Google отдают
`access-control-allow-origin: *`, проверено curl). Браузерный прогон
поймал и убил реальный баг сборки URL (`css2&family=…` → `css2?family=…`).

## История (кратко)

- **v32** — lite-режим: авто-детектор слабого железа + сторож кадров
  (< ~30 fps → lite). Меню при троттлинге CPU 40× и софтверном рендере:
  ~18 → ~57 fps. Полный режим не тронут.
- **v44 «Шёлк»** — пружина позы фишки, плавные состояния; подготовила почву
  для v46 (локальные transition вместо досковых).
- **v45-mixbig** — кап Микса 200 → 600 (галка «Гигантские доски»); фикс
  превью «как бы издалека» (`.is-stale`: старая доска гаснет мгновенно при
  движении слайдера). Производительность на 600 фишках — это уже v46-perf.

## Исследовано, но НЕ слито

- **Миграция позиции фишки на `transform: translate3d(var(--tx), var(--ty), 0)`**
  (экспериментальная ветка, 12 сторожей в `tests/perf44.test.js` — не входит
  в сборку). Сулит быстрый автозум и дешёвые перерисовки, НО требует
  переписать ВСЕ кейфреймы фишек: каждый обязан нести base-translate, иначе
  фишка на кадр «улетает» в угол доски. Риск для вайба высок — отложено.
  Если возвращаться: сначала Закон №0-проверка каждого кейфрейма глазами,
  сторожа уже написаны.

## Как замерять (методика)

1. **Логика**: обернуть в `performance.now()` вызовы `newGame`, `renderFull`,
   `reposition`, `getFreeTiles`, `hasAnyMove`, `countAvailableMoves`,
   `highlightFree` — на самой большой доске (Микс 600, галка «Гигантские
   доски»).
2. **Краска/композит**: DevTools → Performance + Rendering → Paint flashing;
   CPU throttle 4×/20×/40×; на слабых машинах сравнивать с lite-режимом.
3. **Регресс**: `node tests/run.js` (1539) и `node tests/smoke-dom.js`
   (нужен jsdom) — ERRORS: 0.
4. **И ВСЕГДА глазами**: прогнать матч / подсказку / шаффл в Full — картинка
   не должна измениться ни на волос (Закон №0).

## Анти-паттерны — запрещено ЛЮБОЙ оптимизацией

- Убирать или упрощать эффекты, свечения, тени, частицы, звуки в Full.
- Обнулять длительности анимаций вместо починки их стоимости.
- `will-change` на сотнях элементов (200 фишек = 200 GPU-слоёв VRAM).
- Анимировать `box-shadow` / `filter` / layout-свойства (`left/top/width/height`)
  там, где достаточно transform/opacity.
- Полный обход всех фишек на каждый клик или тик.
- O(free²) там, где уже есть O(free).
- Ставить «легче для слабых ПК» выше «так задумано художником»: для слабых
  ПК существует lite-режим — точечно и по решению сторожа, а не огулом.
